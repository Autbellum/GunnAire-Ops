# Existing QuickBooks links through business login

Candidate backend **2026.09.08.43**. This is source qualification, not deployment or full-suite acceptance.

## Actual workflow

An administrator opens **QuickBooks Management → Review existing QuickBooks links**, chooses up to 25 existing customer, item, invoice or estimate links, and reviews the saved and QuickBooks names side by side. A document's original linked customer is included in its batch. Confirming adds only the reviewed shared mappings; it never creates a replacement customer/item/document or changes a QuickBooks price, balance or payment. The unchanged server confirmation rereads exact provider evidence, checks its revision and expiry, and atomically retains one-to-one mappings.

This screen now discovers the connection from the verified business login. Its production path has no device QuickBooks OAuth requirement, fake token, Keychain OAuth load, refresh timer or direct-provider fallback. Test-only fixtures no longer substitute OAuth for the actual screen's connection path.

## Scope and recovery

- `GET /api/qbo-link-reviews/context?companyID=…` accepts exactly the original company UUID. The server requires current administrator access and the original business, derives realm/environment and a public opaque connection revision, and returns only those fields plus protocol version. Discovery reads neither QuickBooks records nor saved review bodies and creates no mappings or review proposals.
- `SharedLinkReviewPreparation` captures the business session, actor, current administrator access and visible page visit before discovery. Invalid company/realm/environment/epoch/version evidence, logout, revoked access and late navigation results cannot create a replacement owner.
- The existing realm/environment/company/actor Keychain journal and operation UUID remain compatible. Discovery does not clear them. Original reviews can be recovered after an uncertain preview/confirmation; confirmed outcomes need no duplicate decision POST. A same-realm reconnection allows historical recovery/cancellation, but an old review cannot be confirmed against the new grant. A fresh batch requires an explicit terminal-review transition.
- Existing local IDs, customer/job relationships, one-to-one identity checks and sold document prices remain unchanged. A changed local link blocks confirmation without destroying the original review; cancellation/recovery remain separate. An old realm's journal is not silently moved to a newly connected realm.
- Native transport admits only bounded exact link-review discovery/lookup/read/preview/confirm/cancel routes using the current business-session bearer. It rejects a general provider proxy, external hosts, redirects, extra/duplicate query fields and oversized requests/responses. The HTTP parser rejects duplicate/nonfinite/deep JSON and caps query fields. No provider credentials are returned or logged.
- The same focused navigation page shows connection failure and an explicit retry; it does not expose a second invoice editor or raw response payload. Leaving the page cancels the owner and prevents late results from repopulating it.

## Research and remaining acceptance

The server retains its existing authorization/access/refresh/revocation lifecycle; [Intuit's official OAuth client](https://github.com/intuit/oauth-pythonclient) documents those responsibilities. This change removes a redundant device-side prerequisite, not the business owner's QuickBooks authorization requirement. Focused status and recovery feedback follows [Apple's feedback guidance](https://developer.apple.com/design/human-interface-guidelines/feedback). [Apple's View body documentation](https://developer.apple.com/documentation/swiftui/view/body-8kl5o) defines the composition layer; the decision to keep authorization/database work out of its eligibility expression comes from the local failure evidence and verified correction, not a claim that Apple documented this exact bug. These sources do not establish this application's compliance or acceptance.

The matching backend must be deployed before production use. No main merge, deployment, live QBO/customer-message/payment mutation, production roster change, signing/capability/schema change or physical installation is part of this checkpoint. Full-suite work remains: signed CloudKit convergence and independent staff sharing; approved real iPad-to-iPhone Tap to Pay/Handoff; remaining device-OAuth-only Google/QBO workflows and account configuration; supplier partner onboarding/ordering; and full competitor-suite, navigation, accessibility and real-device acceptance.

The next CloudKit audit has concrete source evidence: `GunnAireCloudKit.productionModelConfiguration` uses a private database; `CompanyWorkspaceAccess` requires the single approved account hash; the backend refuses a different account binding without reviewed migration. There are no `CKShare` or shared-database consumers in the native source. This is an architectural multi-user gap, not merely an unverified signing setting. Apple's [SwiftData configuration options](https://developer.apple.com/documentation/swiftdata/modelconfiguration/cloudkitdatabase-swift.struct?changes=_4) expose automatic/private/none, while [CloudKit sharing](https://developer.apple.com/documentation/CloudKit/shared-records?changes=l_9) uses explicit shares and participants. Because a write participant can alter or delete every included record, a company-wide read/write share alone would not enforce the app's technician/accounting restrictions. Independent staff sharing needs an explicit access/data-ownership design and real multi-account acceptance; neither binding removal nor blanket sharing is a safe shortcut.
